# M2.2 — Write actions on the local node: feature proposal

Status: proposal, not scoped for implementation. Read-only local-node
browsing (M2.1) is a prerequisite and is in progress on a separate branch.

## Summary

M1 and M2.1 are both read-only: M1 browses any public repo through a seed's
HTTP API, M2.1 reads the local node's own storage. M2.2 is the first
milestone where this module *changes state* — creating issues, commenting,
opening and reviewing patches, editing repository metadata — which is a
different trust and safety bar than reading. Every write needs a signing
key, has to survive being interrupted or retried without corrupting state,
and (unlike a read that just fails and retries) can't be silently wrong.

"GitHub-Desktop-style" is the user's own framing for the UX, not the
protocol — Radicle's data model doesn't match GitHub's, and pretending it
does would build the wrong thing. What we take from GitHub Desktop is a set
of interaction habits: keep the terminal optional, not required; before
anything is finalized, show what's about to change (a diff, a comment
preview, a title/description form) rather than acting immediately on a
click; every action has an obvious way to back out; and the interface
starts simple (a text box, a button) with advanced options (labels,
assignees, review scope) tucked behind progressive disclosure rather than
front-loaded into one dense form. Applied here: open a "New issue" panel
with just title + description visible, add a comment inline where you're
already reading, review a patch by annotating the diff you're already
looking at rather than switching to a separate review screen.

## What `rad` CLI can do

Sourced from the Radicle user guide ([HackMD mirror](https://hackmd.io/@radicle/H1QjlQKoT); the canonical `radicle.dev/guides/user` blocks automated fetches, so this is the same content via a community mirror) and a plugin author's documented CLI usage ([radicle-jetbrains-plugin](https://github.com/cytechmobile/radicle-jetbrains-plugin)).

| Area | Write commands | What they do |
|---|---|---|
| Issues | `rad issue open`, `edit`, `comment`, `assign`, `label`, `delete` | Create/modify issues, thread comments, assign to a DID, tag with labels |
| Patches | `git push rad HEAD:refs/patches` (open), `rad patch edit`, `rad patch label`, `rad patch review --accept/--reject`, `git push --force` (update) | Propose a change as a patch, revise it, review with accept/reject, no separate "merge" command — merging happens via the underlying git push once a patch is accepted |
| Repository | `rad init`, `rad id` (delegate/identity management), `rad remote add` | Turn a git repo into a Radicle one, manage repo delegates, track a peer's branches |
| Network/seeding | `rad seed`, `rad seed --delete`, `rad follow`, `rad unfollow`, `rad block` | Control what your node replicates and from whom |
| Node | `rad node start`, `rad auth` (create identity/keypair) | Start the local daemon, create the signing identity |

Two things worth flagging for scoping: **patch merge is implicit in
acceptance + a git push**, not a distinct "Merge" API call the way GitHub's
is — our core module will need to model that as a sequence, not a single
write method. And **`rad auth` (identity/keypair creation) is arguably
outside this module's scope** — Radicle assumes the user already has an
identity and a running node (per this project's own stated M2 assumption:
"user set up local `rad` node manually"), so M2.2 should assume a signer
already exists and surface a clear error if it doesn't, not offer to create
one.

## What Radicle Desktop already surfaces

Radicle's own GUI ([radicle-dev/radicle-desktop](https://github.com/radicle-dev/radicle-desktop)) is the most directly relevant prior art — it's the reference implementation of "what does a Radicle GUI make write-capable." Its README doesn't document a feature list in prose, so most of this was inferred from its source tree structure; two live screenshots (below) confirm and sharpen part of that inference.

- Built with **Tauri + Rust + Svelte**, not a wrapper around the `rad` CLI or a webview over `radicle-httpd`. This matters for us: the reference GUI talks to the node through Rust directly, the same shape M2.1 is already building for reads. **Unconfirmed**: whether it also shells out to `rad`/git for some operations (e.g. the patch-merge-via-push case above) — the README didn't say, and I didn't dig into the Rust source.
- `src/modals/CreateIssue.svelte` exists as a dedicated component — issue creation is a modal overlay on the current view, not a separate page/route. **Confirmed by screenshot**: the "New issue" modal is exactly title (single line) + description (multi-line, "Markdown is supported") + "Add labels" / "Add assignees" as separate buttons below the description, not inline form fields — matching this proposal's #1/#3 split (create vs. label/assign as distinct actions) rather than one dense form. Worth copying this shape closely: it's a direct, working example of the "simple by default, advanced tucked away" principle this proposal argues for on general GitHub Desktop grounds.
- `src/views/repo/` has `Issue(s).svelte`, `Patch(es).svelte`, `RepoCommit(s).svelte` — matching this module's own tab structure closely (we already have `IssuesTab`, `PatchesTab`, `CommitsTab`). No dedicated "review" or "comment" view file was visible in the one directory level I checked, suggesting those are likely inline UI within `Patch.svelte`/`Issue.svelte` rather than separate screens — **unconfirmed**, I did not open those files.
- **Confirmed by screenshot**: the empty-state Patches tab shows the exact instructions for opening a patch without any in-app action — "Create a new branch in your working copy, commit your changes, and run: `git push rad HEAD:refs/patches`" — which is a direct, live confirmation of feature #6's git-push caveat below: Radicle Desktop itself does not offer an in-app "create patch from this branch" button today, it tells the user to use git directly. Same screenshot's "Don't have a working copy yet? ... `rad checkout rad:<id>`" matches the checkout affordance already scoped into M1.1 (see CLAUDE.md's M1.1 section) for read-only browsing — worth reusing the same UI pattern/copy for consistency between M1.1's read-side "get a working copy" prompt and M2.2's write-side "open a patch" prompt, since Radicle Desktop treats them as the same kind of instruction (a command to run outside the app), not two different features.
- No evidence found (in the README, the directories checked, or the screenshots) of a repository-settings/delegate-management UI, seeding-policy UI, or identity-management UI — **unconfirmed** whether these exist elsewhere in the app; could not verify either way from what was fetchable.

## GitHub Desktop's UX patterns worth borrowing

Not GitHub's protocol — Radicle has no forks, no server-side PR object, no
required-reviewers gate — but these interaction patterns translate:

- **The changes view is the default view, not a mode you switch into.** Opening a repo in GitHub Desktop shows you what's different right now; committing is a natural next step from looking at a diff, not a separate "start a commit" flow.
- **Commit message has a required summary line and an optional, visually secondary description field.** Directly reusable for issue/patch titles vs. descriptions.
- **A PR review is done by clicking directly on a diff line to add a comment, then submitting the whole review (approve/comment/request changes) as one action once you're done annotating**, rather than posting each comment individually. This maps well onto `rad patch review` — collect inline comments against hunks, then submit the review with its outcome as one act, matching `rad`'s `--accept`/`--reject` review model instead of the noisier "comment on every line separately" pattern some tools use.
- **Every mutating action shows a confirmation state that's cancellable up to the point of commit** — e.g., you can amend or discard a commit message before it's actually created. For Radicle this argues for a compose-then-confirm shape (write the issue, see a preview, then "Create issue") rather than creating on first keystroke.
- **Branch/PR switching never loses unsaved work silently** — GitHub Desktop stashes or warns. Directly relevant if a user is mid-comment and navigates away.

## Proposed M2.2 feature set

Phrased as user-facing capabilities. "New core API" means something beyond
what M2.1's read-only `local*` methods will already provide.

| # | Feature | New core API? | Complexity | Radicle-specific wrinkle |
|---|---|---|---|---|
| 1 | Create a new issue (title + description) | Yes — `localOpenIssue` or similar, wrapping `radicle` crate COB writes | Small | None significant — closest to a 1:1 GitHub Issues mapping |
| 2 | Comment on an existing issue or patch | Yes — `localCommentOn(rid, cobId, body)` | Small | Comment threading in Radicle's COB model may be flatter or differently-nested than GitHub's; needs checking against the crate's actual comment/reply shape before committing to a UI thread structure |
| 3 | Label / assign an issue | Yes — small additive write methods | Small | Assignment is by DID, not a username — needs a picker sourced from known peers/delegates, not free text |
| 4 | Edit an issue's title/description | Yes | Small | — |
| 5 | Review a patch: inline comments on a diff hunk, submitted with accept/reject | Yes — likely the largest new API surface, since it needs hunk-addressable comment writes | Large | `rad`'s review model is accept/reject at the revision level with a written verdict, not GitHub's three-state (approve/comment/request-changes) — UI copy and states need to match Radicle's actual semantics, not GitHub's, or the UI will promise something the protocol doesn't do |
| 6 | Open a patch from a local branch | Partially — the "open" step is `git push` to a magic ref, not a COB write; core module needs a way to shell out to git or replicate that push via the crate | Medium | This is fundamentally a git operation wearing a COB hat — worth confirming whether the `radicle` crate exposes a direct API for it or whether the implementation genuinely needs to invoke git push, which has different error-handling and signing implications than a pure COB write |
| 7 | Update a patch (push a revision) | Same as #6 | Medium | Same git-push caveat |
| 8 | Merge an accepted patch | Possibly none beyond #6/#7's git plumbing — merge is "accept + push", not a distinct write | Medium | Make sure the UI doesn't imply a single atomic "Merge" button does something the protocol can't — it's a sequence (review accept, then a push), and partial failure between the two steps needs a clear state, not a silent inconsistency |
| 9 | Repository/delegate identity management (`rad id`) | Yes, but likely out of scope for a first cut — see phasing | Large | Multi-delegate quorum semantics are genuinely more complex than anything in GitHub's mental model; don't attempt a simplified GitHub-style "add collaborator" button without first understanding Radicle's threshold-signature delegate model, or the UI will lie about what it's actually doing |

## Suggested phasing

**M2.2a (first cut):** #1–4 — issue creation, commenting, labeling,
editing. All are COB-only writes with no git-push entanglement, all map
closely to a GitHub Issues mental model, and together they're enough to
make the module genuinely useful for triage/discussion without touching
the harder patch-review or identity-management surface.

**M2.2b:** #5–8 — patch review and the git-push-adjacent operations
(opening/updating/merging patches). Larger because of the diff-hunk
comment UI and the git-plumbing question in #6/#7 that needs answering
before implementation, not during it.

**Explicitly deferred, needs its own scoping pass:** #9, delegate/identity
management. Different risk profile (governance-affecting, not
content-affecting) and Radicle's model doesn't have a clean GitHub
analogue — a rushed "just add the obvious button" here is likely to be
wrong in a way that matters more than a rough edge in issue commenting
would.

## Open questions

- **Signing UX**: how does the app prompt for/hold the signing key for a
  write? Radicle's CLI assumes an unlocked `rad auth` session; does this
  module's core layer need to handle a passphrase prompt itself, or can it
  assume the local node's signer is already unlocked (matching this
  project's stated assumption that the user manages their own `rad` node)?
  This affects every write feature, not just one — worth deciding before
  M2.2a starts, not per-feature. **Live data point**: the user reports
  Radicle Desktop itself prompted for the `rad` passphrase on startup when
  `rad auth` was needed — so the reference GUI does NOT assume an
  already-unlocked signer, it owns a passphrase prompt of its own. That's
  a real precedent to follow rather than assuming this module can skip the
  problem by requiring the node be pre-unlocked; M2.2a should budget for a
  passphrase-entry UI (Basecamp module, not `rad` CLI) as part of its
  first-cut scope, not a deferred nice-to-have.
- **Failure and retry semantics for multi-step operations** (patch
  open/update via git push, merge via accept+push): what does the UI show
  if step one succeeds and step two fails? GitHub Desktop's answer
  (leave you in a recoverable, clearly-labeled state, never silently
  retry) is the right target, but the specific states need mapping against
  what the `radicle` crate actually reports on partial failure.
- **Comment/review data shape**: confirm the `radicle` crate's actual COB
  schema for comments and reviews (nesting depth, whether inline-hunk
  comments are a distinct object type from top-level comments) before
  committing to a UI thread/annotation model — this proposal's feature
  descriptions above are intentionally written at the user-facing level so
  they survive that detail turning out differently than guessed.
- **Multi-delegate repos**: even before attempting #9's write support, do
  M2.2a/b's read-adjacent UI (e.g., "who can I assign this issue to")
  need to account for a repo having more than one delegate? If M2.1's
  local-read work already surfaces delegate lists, M2.2a can reuse that;
  if not, it's a small additional read dependency to sort out first.
