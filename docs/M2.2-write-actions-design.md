# M2.2 — write actions: design and scope

Status: design, with the first vertical slice implemented against it.
Supersedes the open questions in
[`M2.2-write-features-proposal.md`](M2.2-write-features-proposal.md), which
stays as the record of the feature survey and the prior-art research. This
document is the part that had to be settled by reading the `radicle` crate and
probing a real profile rather than by inference.

M2.1 (read-only local browsing over a Rust FFI into the `radicle` crate) is
merged and is the foundation this builds on. Everything below assumes it.

## What the read layer already gives us, and what a write needs on top

M2.1's Rust crate (`radicle/rust-ffi/`) opens storage with

```rust
Storage::open(&storage_dir, UserInfo { alias, key })   // local.rs
Issues::open(&repo, store::access::ReadOnly)            // cobs.rs
```

`ReadOnly` is a zero-field unit struct, so **nothing in the read path holds a
signer** and nothing can prompt for a passphrase. That is the property M2.1
deliberately established, and it is exactly the property a write does not have.

A write needs three things the read path does not:

1. **A signer.** `store::access::WriteAs::new(&signer)` in place of `ReadOnly`.
2. **A cache handle.** Every mutating COB method takes `&mut impl cob::cache::Update`.
   `cob::cache::NoCache` satisfies it, so M2.1's "own no SQLite file" decision
   carries straight over to writes.
3. **Optionally, an announcement.** Purely optional — see below.

Everything else is the same objects the read path already opens.

**The write API is already exercised in this repository.** `rust-ffi/tests/cob_reads.rs`
creates its fixtures through `Issues::open(&repo, WriteAs::new(&signer))`,
`store.create(...)` and `issue.comment(body, root, [])`. So the mechanics of a
COB write are not an unknown — they are load-bearing in the existing test suite.
What was genuinely unknown, and what this design had to settle, is **where the
signer comes from on a real machine**.

## Signing: the finding that changes the scope

The prior proposal recorded a live data point — Radicle Desktop prompts for the
`rad` passphrase on startup — and concluded that M2.2a "should budget for a
passphrase-entry UI as part of its first-cut scope, not a deferred
nice-to-have."

That conclusion is too strong, and a probe against a real profile is what shows
why. `Profile::signer()` (`radicle-0.25.1/src/profile.rs:324`) picks one of
three sources:

```rust
let source = if self.keystore.is_encrypted()? {
    env::passphrase().map(KeystoreEncrypted).unwrap_or(Agent)
} else {
    KeystorePlain
};
```

So there are three states, not two:

| Keystore | `RAD_PASSPHRASE` | ssh-agent holds the key | Signer available? |
|---|---|---|---|
| plaintext | — | — | **yes**, no prompt |
| encrypted | set | — | **yes**, no prompt |
| encrypted | unset | yes | **yes**, no prompt |
| encrypted | unset | no | **no** — a passphrase is genuinely required |

`radicle/rust-ffi/examples/probe_signer.rs` reports which state a machine is
in. On the machine this was designed on:

```
secret key: ENCRYPTED (a passphrase or ssh-agent is required)
RAD_PASSPHRASE in env: false
ssh-agent: reachable
ssh-agent HOLDS this profile's key — writes are signable
```

That is the ordinary post-`rad auth` state: `rad auth` adds the key to
ssh-agent, and it stays there for the session. **The common case needs no
passphrase prompt at all.** Radicle Desktop's startup prompt is the app
covering the *fourth* row — a fresh session where the agent has not been
primed — not evidence that every write needs a prompt.

Two facts make the agent path work from inside Basecamp specifically, and both
were checked rather than assumed:

- `Agent::connect()` reads `SSH_AUTH_SOCK` from the process environment.
  Basecamp inherits the session environment, so the module inherits the socket.
- Asking the agent whether it *holds* the key is a different question from
  whether an agent is *running*, and only the first one predicts a successful
  write. The probe asks the second question via `agent.into_signer(key)`, which
  is the same call `Profile::signer()` makes.

### What this milestone does about it

**Report the state; do not build a passphrase UI yet.**

`getCapabilities()` already declares a `canWriteLocal` field that has been
hardcoded `false` since M1 with the comment "writes arrive in a later
milestone". This milestone makes it truthful: it becomes a real probe of
whether a signer can be obtained, and a new `writeUnavailableReason` says why
when it cannot.

That is the honest shape for three reasons:

- The common case is already signable, so a prompt would be UI nobody sees.
- A passphrase-entry UI is not free to get right — it means holding a secret in
  QML memory, deciding a cache lifetime, and deciding what happens on a wrong
  passphrase. That is its own change, and it should not be smuggled in beside
  the first write.
- A wrong answer here is invisible in the worst way. If the module claimed it
  could write and then failed at signing time, the user would lose a composed
  comment to an error they could do nothing about. Probing up front means the
  compose box is never offered when it cannot be submitted, which is the
  "fail safely" half of the UI requirement.

The passphrase prompt is therefore **deferred, with the reason recorded and the
capability field already in place to drive it**. When it is built, nothing in
the API shape below changes: it fills in the fourth row of the table.

## What a COB write actually does, on disk and on the network

Confirmed by reading the crate, because "does this reach the network" decides
whether writes need the node daemon running:

- **A COB write is a local git operation.** `grep announce` over
  `radicle-0.25.1/src/cob/` returns nothing; announcing lives entirely under
  `src/node/`. `store.create(...)` / `issue.comment(...)` append a signed
  operation to the DAG under `refs/cobs/<typename>/<id>/...` in local storage
  and return. **Writes work with the node stopped**, which matters because
  M2.1's whole local surface already works offline and a write that silently
  required a daemon would break that promise asymmetrically.
- **Announcing is a separate, optional step**, through the node's control
  socket: `Handle::announce_refs_for(rid, namespaces)` is one round-trip
  (`node.rs:1396`). `Node::announce` — the richer one — subscribes to an event
  stream and blocks until seeds acknowledge or a timeout expires, which is
  wrong for a synchronous FFI call and is not used.
- **No separate `sign_refs` step is needed.** The test fixture calls
  `sign_refs` after a raw `git push` into storage, because that push bypasses
  the crate; the COB store's own write path signs as part of the operation.

So the module's write does the local write first, then attempts an announce and
treats its failure as non-fatal. A comment that is stored locally but not yet
announced is a normal Radicle state — the node announces on next start — and
reporting it as a failed write would be wrong and would invite the user to
write it twice.

The reply carries both facts:

```json
{"id":"<comment oid>","announced":true}
{"id":"<comment oid>","announced":false,"announceError":"node is not running"}
```

## API shape

Consistent with the module's existing conventions (`radicle_impl.h`): a
`local*` name, a JSON string reply, `{"error":"..."}` on failure.

```cpp
/// Post a comment on an issue's discussion thread. Local-node only.
std::string localCommentOnIssue(const std::string& rid,
                                const std::string& id,
                                const std::string& body);
```

Four decisions inside that one signature:

- **`local` prefix, and no `remote` counterpart.** The seed API rejects writes
  with HTTP 405 — `radicle_impl.h` says so in its header comment. Adding
  `remoteCommentOnIssue` to keep the surfaces symmetric would create a method
  whose only possible behaviour is failure. The asymmetry is the honest
  representation, and it is why the source split exists at all.
- **Comment, not `commentOn(rid, cobId, body)` generically.** Issues and
  patches look alike at the read layer because the seed flattens them, but they
  are different COB types with different stores and, for a patch, a comment
  belongs to a *revision* rather than the object. One method per type keeps the
  next one from having to reinterpret an overloaded id.
- **Reply-to is not a parameter.** The comment lands on the thread root.
  `ThreadView.qml` renders a flat list and reads no `replyTo`; a parameter the
  view cannot produce and the view cannot display would be dead API. Threaded
  replies are a UI feature first and an API change second.
- **No embeds.** The crate's `comment(body, replyTo, embeds)` takes attachments.
  Nothing in this module can produce one.

The QML side needs no new plumbing: `Main.qml`'s `call()` already takes a
`source` parameter, and `SourceState.methodFor()` already routes by prefix.
A write call is `app.call("CommentOnIssue", [rid, id, body], ok, fail)` under
the local source.

### How "no local node" surfaces

Three distinct refusals, deliberately not collapsed into one:

| Situation | Where it is caught | What the user sees |
|---|---|---|
| No profile at all | `radicle_impl.cpp`, before the FFI | `LocalStore::unavailableReason()`, as every `local*` method already does |
| Profile, but no obtainable signer | Rust, at signer load | "your Radicle key is encrypted and ssh-agent does not hold it — run `rad auth`" |
| Browsing the remote source | QML, before any call | the compose box is not rendered |

The third one is the important one for the "fails safely" requirement. The
compose box is bound to a capability, not merely disabled on error: a user
browsing a seed-hosted repo never sees an affordance that could not work,
because the repo they are looking at may not exist in local storage at all.

## Scope: what is in M2.2, what is not

The instruction was the narrowest genuinely-useful vertical slice, proven end
to end, over a broad half-wired surface. That is **commenting on an issue**.

**In scope, implemented:**

- `localCommentOnIssue` — Rust write, FFI entry point, `LocalWriter` C++ class,
  `radicle_impl.cpp` method, `.rep` slot, backend forwarder, QML compose box in
  `ThreadView`, tests at every layer.
- `getCapabilities().canWriteLocal` made truthful, plus
  `writeUnavailableReason`.

**Deferred, with reasons:**

- **Creating an issue.** Mechanically the same call shape (`store.create`), but
  it needs a modal with title + description, an entry point on `IssuesTab`, and
  a decision about where the new issue lands in a list the user is looking at.
  That is a UI change of similar size to the comment box on top of a second
  write path. It is the obvious next slice.
- **Commenting on a patch.** A patch comment attaches to a *revision*, and
  `get_patch` currently serializes revisions without their discussion threads
  (`cobs.rs` says so, deliberately — "adding them would put unread data across
  the QtRO boundary for every patch open"). So a patch comment box has nowhere
  to render its result. Read support has to come first, which makes this a
  larger change than it looks.
- **Close / reopen an issue.** `issue.lifecycle(State::Closed { reason })` is
  one call. Deferred not for difficulty but because it is a state change with
  no undo affordance designed yet, and because the first write shipping should
  be the one whose failure mode is "a comment did not post".
- **Labels, assignees, reactions.** Assignment is by DID and needs a peer
  picker sourced from delegates; labels need a set the module does not read
  today.
- **Patch review, opening/updating/merging patches.** Unchanged from the
  proposal's M2.2b. The git-push half is genuinely a different subsystem.
- **A passphrase-entry UI.** See the signing section.

## Test plan, by layer

Matching the repo's rule that the change introducing behaviour is the change
that pins it down, and its rule about fakes that answer the same for every
input.

- **Rust (`rust-ffi/tests/cob_writes.rs`).** Against a real fixture profile:
  a comment appears in the thread the read path returns; a comment on an absent
  issue errors rather than silently doing nothing; an empty body is refused; a
  bad rid/id errors; the write is visible to a *fresh* read (i.e. it was
  persisted, not merely returned).
- **Rust (`tests/panic_guard.rs`).** The write entry point joins the existing
  pathological-input sweep, because `guarded()` is a soundness guard and a new
  `extern "C"` function that skips it is undefined behaviour, not a bug.
- **C++ (`radicle/tests/`).** The boundary: the call crosses into Rust, returns
  owned parseable JSON, does not leak; and the no-profile path returns the
  module's error shape rather than crashing.
- **QML (`radicle-ui/tests/`).** The compose box's own behaviour: hidden when
  writes are unavailable, hidden on the remote source, refuses an empty body,
  clears on success, keeps the draft on failure (losing a composed comment to
  a transient error is the failure this must not have), and reloads the thread
  so the new comment appears.

The QML fakes return input-dependent replies — a thread whose comment count
changes after a successful post — so a test can tell "reloaded" from "never
reloaded". A fake returning the same thread every time would pass whether the
reload happened or not, which is the trap that cost this repo a whole
milestone's headline feature.
